\begin{abstract}
Researchers choosing an AI benchmark need to find its tasks, released artifacts, and reported model results. Benchmark Radar brings this evidence into one searchable catalog while preserving each source record and its citations. At the \datacutoff{} cutoff, the catalog contains \ReportNumber{\ReportCatalogCount} benchmark records across \ReportCatalogSourceCount{} sources, with \ReportNumber{\CensusNumericScores} numeric score observations on \CensusScored{} records. The remaining \CensusUnscored{} records have no numeric score; \CensusNoScoreWithLinks{} of them still provide a paper, repository, or dataset link. A score-only catalog would lose these routes to prior work. Across the full catalog, we distinguish models with reported scores from cited documents and measure the availability of score scales and dates. Missing metadata limits comparisons without removing the underlying evidence. A contributor's prior-art search illustrates how to inspect candidates before selecting evaluations. Readers can access the same benchmark records through the dashboard, downloads, and offline search clients.
\end{abstract}

\section{Introduction}

Before designing a new evaluation, a researcher needs to know which benchmarks already test the proposed capability, whether their data and code are available, and which models have been evaluated on them. Answering these questions requires following evidence across paper servers, code repositories, dataset hubs, leaderboards, and model reports. A benchmark name alone rarely supplies the test version, released artifacts, and evaluation settings needed to judge whether it fits the research question.

The range of evaluation tasks makes this search difficult. MMLU \citep{hendrycks2021mmlu}, GPQA \citep{rein2023gpqa}, and Humanity's Last Exam \citep{phan2025hle,zhou2026asi} test knowledge and reasoning. SWE-bench tests issue resolution \citep{jimenez2023swebench}; LiveCodeBench uses date-based code-generation tests \citep{jain2024livecodebench}; and Terminal-Bench and Long-Horizon-Terminal-Bench evaluate command-line agents \citep{merrill2026terminalbench,li2026long}. Researchers must also find domain-specific tests, including FinanceBench \citep{islam2023financebench}, MATH \citep{hendrycks2021math}, SciBench \citep{wang2023scibench}, LAB-Bench \citep{laurent2024labbench}, and ChemBench \citep{mirza2025chembench}. Choosing among them requires inspecting tasks, scoring rules, and released artifacts.

LLM Stats, OpenCompass, and Artificial Analysis provide benchmark catalogs, evaluation platforms, and model comparisons \citep{llmstats2026benchmarks,opencompass2026datasetstatistics,artificialanalysis2026methodology}. Benchmark Radar builds on their records by adding daily discovery and model-report evidence to a shared search interface. A reader can retrieve a benchmark, follow its paper and artifact links, and inspect which reports mention it and under which settings they report scores. Each source record keeps its identity and citations so the reader can trace a result back to the evidence.

We examine what researchers can learn from the complete catalog, including records with missing scores or citations. The census separates benchmark coverage, model coverage, and document coverage, then identifies which measurements support comparisons. The central finding is practical: \CensusNoScoreWithLinks{} records with no numeric score still offer links for a prior-art search. Restricting discovery to scored evaluations would hide them. Appendix~\ref{app:use-case} follows a contributor who used Benchmark Radar to investigate a proposed evaluation.\footnote{Source code: \url{https://github.com/ktwu01/benchmark-radar}.}

\section{Methodology}

\subsection{One Catalog and Its Reader Interfaces}

Benchmark Radar adapts BuilderPulse's daily public-source collection approach \citep{builderpulse} to benchmark discovery. Four sources contribute benchmark records to a common catalog: LLM Stats, OpenCompass Hub, Artificial Analysis, and Model reports. The normalization step preserves one record per source benchmark, its numeric observations, model identities, documents, and citations. Model reports include model cards, technical reports, system cards, and release posts \citep{mitchell2019modelcards}. Document types describe the evidence available for a record.

A benchmark belongs in the catalog even if it has no score, known date, or cited document. Reviewed identity links connect related records without combining their scores or transferring model and document counts. The same benchmark IDs reach web search, detail pages, offline clients, and the exported catalog. Table~\ref{tab:reader-questions} summarizes the reader interfaces.

Benchmark Frontier, on the Leaderboard tab, requires a numeric score and excludes known pre-2024 benchmarks. It retains scored records with unknown dates or counts through labelled marks, and keeps unverified scales outside Pareto calculations. Its initial score cutoff is 70. The linked score ranking retains its date and numeric-score requirements independently of that cutoff. General catalog search and exports retain the full population. The census in this paper applies none of these display filters.

\subsection{Discovery Evidence and Source Health}

Daily discovery observations describe mentions, releases, and updates found across public sources. An observation is one collected record; an artifact is a paper, repository, dataset, release, or page linked by exact identifiers. These objects differ from source-specific benchmark records. We retain their histories alongside the catalog without adding discovery observations to the benchmark total.

Each collection run searches a 48-hour window, records counts and errors by source, removes future-dated rows, and requires healthy core sources before publication. At the cutoff, arXiv \citep{arxivapi}, Hugging Face Hub \citep{huggingfacehub}, and GitHub Search \citep{githubsearchdocs} were the core sources. Additional routes cover scholarly indexes, dataset hosts, repository releases, and institutional feeds. Appendix~\ref{app:source-inventory} records their cutoff status.

The \datacutoff{} snapshot records 1,003 fetched rows and 954 candidates after duplicate removal. Of these, 366 qualified for publication and 138 met the recommendation threshold. These are discovery-run counts, separate from the benchmark catalog census. Published evidence retains source URLs, retrieval times, parser versions, identifiers, and payload checksums. Raw responses and credentials remain outside the public artifact.

\subsection{Identity and Search}

The resolver links discovery observations that share a DOI, arXiv identifier, OpenReview identifier, GitHub repository, or Hugging Face artifact. Similar titles alone do not force a merge. Catalog identity review also preserves each source record; a link to another record does not establish equivalent test versions or protocols.

Lexical search retrieves candidates across all \ReportNumber{\ReportCatalogCount} records. BM25F supplies the primary retrieval score, with bounded boosts for name and phrase matches. Results expose matched and missing query tokens, fields, coverage, and score components. Source membership does not change ranking. The shared query service supplies CLI and HTTP responses with local data provenance and retrieval mode. Installed clients search offline and update through explicit initialization or synchronization.

A separate priority score for daily recommendations combines relevance (35\%), evidence (20\%), recency (20\%), and adoption (25\%) on a 0--100 scale. These weights describe reading priority for discovery observations. An agent assessing benchmark suitability can try focused query variants, inspect record details, and read the cited sources; that judgment occurs after candidate retrieval.

\subsection{Measurement Rules for the Full-Catalog Census}

We start with every record in the rebuilt \texttt{benchmark-index.json} and read its own detail shard. We count finite numeric score observations once by observation ID. For each benchmark record, we count distinct scored models by source model ID, preserving separately evaluated configurations, and cited documents by document ID. Repeated scores or documents for a model do not increase that record's model count. Missing model identities or absent measurements remain unknown. The global model registry uses its recorded identity links; we do not sum per-benchmark model counts to obtain a global total.

We apply score-scale and date requirements to evidence fields across all sources. A declared percentage unit, known score direction, and values within 0--100 support a percentage-scale summary. A display rescaling or an aggregator's declared maximum alone does not verify a percentage metric. Even a valid percentage scale does not establish matching instruments, prompts, tool access, attempts, or evaluators \citep{gebru2021datasheets,mitchell2019modelcards}.

For date coverage, we count recorded benchmark release dates without substituting crawl times or model release dates. Score entries carry their date basis separately. A model's announcement date can provide a labelled timeline proxy; it cannot establish when a benchmark score was measured or published. Missing metadata restricts the calculation that needs it while leaving the source record and numeric observations inspectable.

The sources differ in the evidence their snapshots contain. LLM Stats supplies benchmark descriptions and reported results \citep{llmstats2026benchmarks}. Of the \CensusUnscored{} unscored records, \CensusNoScoreWithLinks{} have at least one paper, repository, or dataset link. Across the full catalog, \CensusPaperLinks{} records have a paper link, \CensusRepoLinks{} have a repository link, and \CensusDatasetLinks{} have a dataset link; the categories overlap. For example, the OpenCompass Hub record for A-Bench links a paper, code repository, and dataset despite having no archived score. These links give researchers routes to inspect tasks and baselines before deciding whether an evaluation fits their work. Link presence does not establish current availability or permission to use an artifact.

\subsection{Models and Documents Measure Different Kinds of Coverage}

The common document registry contains \ReportNumber{\CensusDocuments} distinct cited documents, attached to \ReportNumber{\CensusDocumentsKnown} of the \ReportNumber{\CensusRecords} benchmark records. Five records have no cited documents. The shared model registry contains \CensusModels{} model identities. Within the catalog, all \CensusScored{} scored records have sufficient model IDs to count distinct models; unscored records have unknown scored-model coverage.

The Artificial Analysis record for GPQA Diamond contains scores for 586 models and cites one registry page. The catalog records benchmark release dates for \CensusReleaseKnown{} records, leaving 668 without a release date. Across score observations, 12,594 entries carry model-announcement dates and 322 carry document-publication dates. Neither date basis directly establishes an evaluation date. This archive therefore cannot support a catalog-wide claim about score stagnation from a gap between model-report mentions and score-entry dates. Researchers must first establish dates and comparable evaluation settings for the relevant source records.

A small gap to a metric ceiling can describe a reported setup. It does not show that a benchmark has exhausted its ability to distinguish models across versions and settings. Catalog-wide headroom or recency estimates require the eligible measurement coverage alongside the statistic.\footnote{Junjie Zhou contributed a score-archive audit and earlier report revisions, documented in \href{https://github.com/ktwu01/benchmark-radar/issues/457}{issue~\#457}.}

\section{Limitations and Future Work}
\label{sec:caveat-future-work}

Lexical search can miss paraphrased benchmark names, renamed tasks, or descriptions of related ideas. Semantic retrieval could broaden the candidate set while preserving source links and retrieval explanations \citep{reimers2019sentencebert}. The worked example combines catalog queries with web search; evaluating retrieval quality requires relevance judgments over a broader set of queries and candidate records.

The catalog reflects dated inputs with different collection scopes. Registry snapshots and model reports do not cover the same dates or evaluation settings. Public endpoint limits, failed requests, missing identifiers, and incomplete metadata affect coverage. We retain scores with unknown protocols and scales so readers can inspect them, but we do not treat them as comparable measurements. Matching archive labels alone cannot verify independent repeated runs. Reviewing primary sources for test versions, tools, attempts, evaluators, and score-publication dates remains necessary.

The capability-classification component, KW-Bench, produces \ReportNumber{\CensusUnclassified} unclassified tracks in this rebuild. A classification track represents an artifact or a declared task within a benchmark suite, drawn from discovery evidence. The deterministic null extractor used in CI assigns no capability levels, so this run does not validate capability classification. These tracks do not change the benchmark catalog count.

Our quantitative results describe evidence coverage in this catalog. They do not estimate field-wide benchmark adoption, establish saturation, or measure retrieval precision. The worked example records one contributor's workflow and has no controlled baseline. Broader retrieval evaluation requires reviewed relevance judgments, including results outside familiar benchmark families.

\section{Conclusion}

Benchmark Radar gives researchers access to \ReportNumber{\ReportCatalogCount} source-preserving benchmark records and \ReportNumber{\CensusNumericScores} numeric score observations. The full census shows why discovery must include missing measurements: \CensusNoScoreWithLinks{} unscored records still link to material that researchers can inspect. It also separates model coverage from document coverage and identifies the scale and date evidence needed for comparisons. Researchers can use these records to assemble prior art, inspect evaluation settings, and select evidence for further review. The next priorities are retrieval evaluation with reviewed labels and better measurement metadata across sources.

\section{Reproducibility, Access, and Citation}
\label{app:reproducibility}

This revision audits software commit \gitcommit{} with a data cutoff of \datacutoff{}. A fresh detached checkout passed the six required CI steps in order: linting, formatting checks, catalog normalization, classification, release construction, and tests. All 1,314 tests passed. The dated registry inputs remain the August snapshots registered in \texttt{data/leaderboard\_snapshots.yml}; the September cutoff does not imply that those sources were recrawled on that day.

The data build normalizes the registry and model-report inputs into the shared catalog, then classifies discovery tracks and packages the catalog with checksums. Installed clients validate an update before activating it. The manuscript and its dated analysis files build independently of the software checkout. The census reads \texttt{site/data/benchmark-index.json}, the detail shards under \texttt{site/data/benchmarks/}, and the shared document and model registries. Discovery counts come from the rebuilt \texttt{site/data/radar.json} and dated snapshots. Model reports and score YAML files are normalization inputs, not a separate population for the paper's findings.

The paper repository contains \texttt{scripts/audit\_catalog.py}, which validates IDs and counts, computes the census, and exports \texttt{catalog-data.tex} plus \texttt{evidence/catalog-audit.json}. The JSON includes every source-record key, measurement state, per-record model and document counts, citation IDs, and SHA-256 hashes of the inputs. The script checks score-observation uniqueness, record-to-shard identity, document-registry coverage, and reconciliation of scored and unscored records. Its \texttt{--check} mode compares a fresh calculation against the committed outputs. Figure~\ref{fig:abstract} draws one linked dot per census record in source-key order.

To reproduce, check out software commit \gitcommit{}, install its development dependencies, and run the six-step CI sequence. Run the software's \texttt{scripts/export\_report\_figure\_data.py} and its \texttt{--check} mode to refresh \texttt{figure-data.tex}. From the paper checkout, run \texttt{python scripts/audit\_catalog.py /path/to/software}, then repeat with \texttt{--check}. The README records the commands. Finally, run \texttt{make arxiv}, compile the extracted package, and inspect the rebuilt PDF. Normal paper builds use the committed data and do not refresh the evidence.
